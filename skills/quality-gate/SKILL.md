# quality-gate

> Барьер качества перед продом. Команда узких ревьюеров → адвокат дьявола →
> судья. Запускается ПЕРЕД `git push`. На вердикт BLOCK код в прод не уходит.

---

## Назначение

Единый цикл проверки изменений во всех сферах сервиса, чтобы баги не доходили до
прода (Vercel деплоит из `main`). Прогоняет только ревьюеров тех сегментов,
которых коснулся diff (дёшево и быстро), затем опровергает их выводы, затем
судья выносит финальный вердикт.

**Когда вызывать:**
- Перед каждым `git push` (правило в CLAUDE.md §15b).
- По запросу «прогони quality-gate» / «проверь перед пушем».

**Решение пользователя (зафиксировано):**
- Режим: **on-demand** команда (не жёсткий хук). Жёсткий barrier (pre-push/CI) — позже.
- Строгость: судья **BLOCK только на высоком риске** (см. рубрику ниже).

---

## Рубрика серьёзности (что блокирует)

**BLOCK (высокий риск) — прод закрыт, пока не исправлено:**
- 💸 Траты/лимиты: бесконтрольный запуск Claude, обход «защиты кошелька»,
  частые автозапуски, отсутствие анти-наложения, неверная колонка в
  daily-cap/anti-overlap (`started_at`!), отсутствие лимита токенов.
- 🔒 Безопасность: нарушение RLS owner-only, утечка ключа/секрета в клиент/лог,
  публичная функция без проверки секрета, SSRF, `--no-verify-jwt` там, где не нужно.
- 🧱 Сломанный `npm run build` или падающий pre-commit lint.
- 🗑️ Потеря/необратимое изменение данных пользователя (молчаливое удаление,
  миграция без RLS, FK без учёта soft-delete).
- 📤 Доставка/исполнение сломаны (узел не отправляет, схема падает молча).

**REMARK (средний/низкий) — НЕ блокирует, идёт списком замечаний:**
- Логика edge-cases без риска денег/данных, i18n-пропуски, стиль, дубли,
  читаемость, мелкий UX, производительность без регресса.

Судья блокирует ТОЛЬКО при ≥1 подтверждённом BLOCK-пункте. Иначе PASS + замечания.

## Сегменты и ревьюеры (маршрутизация по diff)

Определи затронутые файлы: `git diff --name-only origin/main...HEAD` (или
неотправленные коммиты / рабочее дерево). Запускай ТОЛЬКО релевантных ревьюеров.

| Затронутые пути | Сегмент | Ревьюер |
|---|---|---|
| `supabase/functions/**`, `src/builder/services/**` | Движок исполнения | `engine-reviewer` |
| `*/migrations/*.sql`, RLS, секреты, `_shared/crypto`,`_shared/auth` | Данные и безопасность | `security-reviewer` |
| `src/builder/**` (UI: canvas/узлы/попапы/CSS) | Builder UI | `ux-interaction-tester` |
| `src/locales/**`, `src/data/**`, контент Atlas | Контент | `content-gap-auditor` |
| `package.json`,`vite.config.js`,`*.css`,bundle,деплой-флаги | Сборка/инфра | `performance-auditor` |

Всегда, независимо от diff: `npm run build` ✅ и pre-commit lint ✅ — иначе сразу BLOCK.

## Конвейер (review → verify → judge)

1. **Сбор контекста**: diff + список изменённых файлов + краткое «что делает это изменение».
2. **Ревью (параллельно)**: для каждого затронутого сегмента — соответствующий
   ревьюер по его чек-листу. Каждый возвращает находки с полем `severity`
   (block|remark), файлом/строкой и предлагаемой правкой.
3. **Адвокат дьявола (verifier)**: берёт КАЖДУЮ находку «всё ок»/«не баг» и
   пытается её опровергнуть (пустой вход, очень большой вход, ошибка сети,
   отсутствие ключа, гонка, повтор по расписанию, не та локаль). А также ищет,
   что ревьюеры пропустили. Подтверждённые риски повышают severity.
3a. При `ultracode` — каждый block-кандидат проверяют 3 независимых скептика
    (правота/безопасность/воспроизводимость); реально, если ≥2 подтвердили.
4. **Судья (`code-judge`)**: агрегирует, дедуплицирует, применяет рубрику →
   **PASS** или **BLOCK** + обязательные правки.

## Формат вывода (всегда)

```
🧪 QUALITY GATE — <PASS ✅ | BLOCK ⛔>

Затронуто: <сегменты> · ревьюеров запущено: N · build: ✅/❌

⛔ Блокеры (если есть) — исправить до пуша:
  1. [сегмент] файл:строка — суть. Правка: …
💬 Замечания (не блокируют):
  • [сегмент] …

Вердикт судьи: <одно предложение, почему PASS/BLOCK>
```

На **BLOCK**: НЕ пушить. Исправить блокеры → прогнать quality-gate заново.
На **PASS**: можно `git push` (+ обновить `tasks/current.md`).
