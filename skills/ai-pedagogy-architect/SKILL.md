# ai-pedagogy-architect

## Назначение
Гарантирует, что любое новое обучение про AI следует правилам из
`docs/learning-design-rules.md`. Не пишет «учебник», а проектирует
practice-driven, верифицируемое, экономически осознанное обучение.

## Когда использовать
- Любой новый tutorial → проектирование структуры
- Новый узел mindmap уровня «концепт» (модель / контекст / план / лимит / vision / ...)
- Расширение learning path под новый профиль пользователя
- Апгрейд существующего материала, который «не зашёл» пользователю

## Когда НЕ использовать
- Чисто архитектурные изменения mindmap (без новой педагогики) → `knowledge-architect`
- Запись готового контента в файл → `mindmap-expander`
- Написание промпта (не обучения) → `prompt-engineer`

## Workflow

### Шаг 1. Топик-фитнес
Прежде чем проектировать обучение — проверь, что тема:
- Стабильна на 3-6 месяцев (модели меняются, но **принцип** — нет)
- Имеет реальный use-case у целевой аудитории
- Не дублирует существующие узлы / tutorials

Если нет — флаг «defer» или «merge с существующим».

### Шаг 2. Уровень и зависимости
- Определи `level` (beginner / intermediate / advanced)
- Найди `prerequisites` среди существующих tutorials
- Если зависимостей > 2 — это сигнал «темя слишком сложна, разбей»

### Шаг 3. Outcomes сначала, шаги потом
Сформулируй 3-5 `outcomes` — что пользователь сможет ПОСЛЕ.
Шаги обучения проектируются от outcomes вспять, не наоборот.

### Шаг 4. Concrete-first структура шагов
- Шаг 1 — конкретный пример (запускаемый промпт / команда)
- Шаг 2 — наблюдай, что вышло (validate)
- Шаг 3 — обобщи правило (теория появляется здесь, не раньше)
- Шаг 4 — попробуй вариацию на своей задаче

### Шаг 5. Failure first
Включи хотя бы один шаг, демонстрирующий **что бывает без этой техники**.
Это лучший способ объяснить «зачем».

### Шаг 6. Verify-блоки
В каждом шаге → `validate`: один конкретный признак успеха.
Это критично для AI-обучения (модель может «уверенно» ошибаться).

### Шаг 7. Cost-awareness
Если шаг подразумевает выбор модели — добавь tradeoff заметку.
«Opus дорого, для этой задачи хватит Sonnet» — это часть обучения, не FAQ.

### Шаг 8. Exercises обязательны
Минимум 2 `exercises[]` для каждого tutorial. Формат: `{question, hint}`.
- Первое — простая перенос на свою задачу
- Второе — комбинация с другой техникой / сценарием

### Шаг 9. Anti-patterns
Опиши 3 `pitfalls` — частые ошибки на этой теме.
Это профилактика, не «правила».

### Шаг 10. ApplyIn — приземление
2-4 `applyIn[]` — реальные кейсы, где это применяется.
Каждый: `{title, description}`. Один из кейсов — командный/коллаборативный.

## Rules

- **Никакой одной «правильной» модели по умолчанию.** Учи выбору.
- **Никаких неподтверждённых цифр** про Opus/Sonnet/Haiku — добавляй
  «требует проверки в docs.anthropic.com» если не уверен.
- **Никаких «Pro обязательно».** Если можно научить на Free — учи на Free,
  обозначь где Pro полезен дополнительно.
- **Структура всегда: concrete → abstract → exercise.**
- **Длина step.why — 1 предложение, не абзац.** «Зачем это» одной фразой.
- **Длина step.instructions — 3-5 пунктов**, не больше.

## Output format

Возвращает готовый объект tutorial (для tutorials.js) или узел (для mindmapData.js)
со всеми обязательными полями. См. `docs/content-rules.md` и
`docs/knowledge-structure.md` для точной схемы.
