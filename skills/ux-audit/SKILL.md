# ux-audit

> Команда UX и product-experience экспертов. Периодический аудит продукта →
> приоритизированные предложения по улучшению. Каденция, а не «когда сломалось».

---

## Назначение

Регулярно (раз в 1–2 недели) смотреть на продукт глазами пользователя и
предлагать конкретные улучшения — до того как проблемы накопятся. Не код-ревью
(это `quality-gate`) и не адаптив (это `mobile-gate`), а **качество опыта**:
понятно ли, легко ли, доходит ли пользователь до результата.

**Когда запускается:**
- По расписанию: GitHub Action `ux-audit.yml` (раз в 2 недели) создаёт
  агенду-документ `docs/ux-audit/ux-audit-{YYYY-MM-DD}.md` (что менялось в UI,
  какие экраны смотреть, чек-лист). Затем Claude по этому скиллу заполняет
  находки и предложения.
- On-demand: «прогони ux-audit» / «сделай UX-аудит экрана X».

---

## Группа экспертов (сегменты)

| Сегмент | Что оценивает | Кто |
|---|---|---|
| Эвристики | 10 эвристик Нильсена, единообразие, предотвращение ошибок | `heuristic-evaluator` |
| Опыт продукта | онбординг, активация, удержание, JTBD, трение, воронки | `product-experience-auditor` |
| Поток/навигация | задачи пользователя, тупики, число шагов | `ux-interaction-tester` (on-demand) |
| Доступность | контраст, фокус, размеры, screen-reader | `accessibility-review` |
| Оформление предложений | decision-ready док с приоритетами | `proposal-generator` |

Запускать релевантных под фокус аудита (весь продукт vs конкретный экран).

---

## Метод (как проводить аудит)

1. **Скоуп**: весь продукт или конкретная зона (Atlas-карта, обучение, Builder).
2. **Пройти ключевые задачи пользователя** (JTBD), отмечая трение:
   - Первый визит → понял ли, что это и что делать дальше.
   - Найти узел/курс → начать обучение → дойти до результата.
   - Builder: собрать схему → запустить → получить результат.
3. **Эвристики**: прогнать `heuristic-evaluator` по затронутым/ключевым экранам.
4. **Опыт**: `product-experience-auditor` — где теряется мотивация, что мешает
   активации/возврату.
5. **Визуальная проверка** (если можно запустить preview) — скриншоты ключевых
   экранов, светлая/тёмная, десктоп + мобайл.
6. **Приоритизация**: каждое предложение → {impact: high|med|low, effort: S|M|L}.
   Вынести **топ-5** (high-impact / low-effort вперёд).

## Формат вывода (в `docs/ux-audit/ux-audit-{date}.md`)

```
# UX-аудит {дата}

## Что смотрели
<скоуп, экраны, задачи>

## Находки (по сегментам)
- [эвристика/опыт] экран — проблема — почему мешает — серьёзность

## Топ-5 предложений (impact × effort)
1. [HIGH/S] … — ожидаемый эффект
...

## Журнал
Связь с предыдущим аудитом: что внедрили, что осталось.
```

Решения логировать в `docs/ux-audit/` (и при необходимости — в
`docs/business-strategy/07-decisions.md`, если влияет на стратегию).

## Принципы
- **Конкретика, не вкусовщина**: каждая правка обоснована эвристикой/задачей/данными.
- **Приоритеты, а не список**: founder получает топ-5, а не 50 пунктов.
- **Не ломать философию**: см. `docs/strategy/01-positioning.md` (никаких «курсов/
  академий»), `docs/learning-design-rules.md`.
- Реализация принятых правок — через обычный цикл (skill + `quality-gate`/`mobile-gate`).
