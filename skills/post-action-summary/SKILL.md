# post-action-summary

> **Постоянное правило поведения.** Применяется автоматически после каждого
> значимого действия в проекте. Не опционально.

---

## Главный принцип (читать первым)

После каждого действия есть **два слоя информации**, и их нельзя смешивать:

1. **Итог для человека** — то, что я пишу пользователю в чат.
   **Простыми словами. Без единого термина разработчика.** Как будто
   объясняю другу, который не программист: что изменилось, почему это нужно,
   на что влияет. Несколько коротких предложений.

2. **Технические детали** — имена файлов, названия функций, хеши коммитов,
   термины. Это **НЕ для чата**. Это уходит в:
   - текст git-коммита (там термины уместны — это для истории кода),
   - при необходимости — в `docs/` или `tasks/`.

**Правило №1:** если пользователь — обычный человек, он должен понять итог
**без гугления слов**. Никаких «RLS», «bundle», «edge function», «props»,
«endpoint», «localStorage», «topological sort» в чате. Только в коммите.

---

## Когда применять

После **каждого** из этих типов действий:

- ✅ Сохранённое изменение в коде
- ✅ Создание / удаление / перемещение файла
- ✅ Изменение того, как устроен проект
- ✅ Настройка системы (автоматизации, проверки, окружение, публикация)
- ✅ Завершение этапа работы
- ✅ Обновление содержимого (темы, обучалки, шаблоны)
- ✅ Изменение внешних компонентов, от которых зависит проект
- ✅ Запуск / изменение AI-помощников (скиллов)
- ✅ Создание стратегического документа
- ✅ Любое действие, которое меняет состояние проекта

**Когда НЕ применять:**
- ❌ Просто читал файлы, ничего не менял
- ❌ Уточняющие вопросы к пользователю
- ❌ Один крошечный правка, где итог длиннее самой правки

---

## Формат итога для человека (основной — всегда в чат)

Три простых блока. Простой язык. Без терминов.

```
✅ Что изменилось:
[1-3 предложения. Что теперь по-другому — словами, понятными любому.]

💡 Почему так лучше / зачем:
[1-2 предложения. Какую проблему это решает в реальной жизни.]

➡️ Что дальше:
[Логичное продолжение. Понятное действие.]
```

Если есть **риск или важное предупреждение** — добавить блок:

```
⚠️ Важно знать:
[Простыми словами. Что может пойти не так или о чём помнить.]
```

Если затронуты **деньги, безопасность или приватность данных** — обязательно
сказать об этом простыми словами в «Что изменилось» или «Важно знать»
(например: «теперь данные хранятся в облаке, доступ — только у владельца»,
а не «added RLS policy»).

---

## Формат технических деталей (НЕ в чат по умолчанию)

Уходит в **текст коммита**. Там можно и нужно: имена файлов, функции, хеши,
слои (frontend/backend/security/...), breaking changes. Пользователь это
видит только если сам откроет git — и это нормально, это для истории кода.

Если пользователь **явно просит** технические детали («покажи технически»,
«что именно в коде») — тогда даю отдельным блоком, помеченным
«🔧 Технические детали:», и только тогда термины разрешены.

## Словарь перевода: термин → простыми словами

Когда тянет написать термин в чат — заменить на человеческое:

| Термин разработчика | Простыми словами |
|---------------------|------------------|
| RLS / row-level security | «каждый видит только свои данные» |
| bundle / chunk size | «сколько весит страница при загрузке» |
| edge function / backend | «программа на сервере» |
| localStorage | «память браузера на этом устройстве» |
| Supabase / database | «облачное хранилище» |
| commit / push | «сохранил изменения» / «отправил в проект» |
| cross-link | «ссылка между темами» |
| component / prop | «элемент интерфейса» / «настройка элемента» |
| cache / caching | «запоминание ответа, чтобы не считать заново» |
| lazy load | «подгружается только когда нужно» |
| migration | «обновление структуры хранилища» |
| auth / OAuth | «вход в аккаунт» |
| API call / token | «запрос к сервису» / «расход на запрос» |
| serialize / deserialize | «упаковать / распаковать данные для хранения» |
| topological sort | «выполнить шаги в правильном порядке» |
| RLS policy / encryption | «правило доступа» / «шифрование» |
| contrast / WCAG | «читаемость текста» / «доступность для всех» |
| refactor | «переписал аккуратнее, поведение то же» |
| deploy | «опубликовал обновление» |

Если нужного термина нет в таблице — придумать понятную замену по тому же
принципу: **что это делает в жизни пользователя**, а не как называется в коде.

## Примеры применения (правильно vs неправильно)

### Пример 1 — обновление содержимого

❌ **Неправильно (термины):**
> Закоммитил cap-tools upgrade — узел получил rich content с JSON schema
> example и cross-links. sync-whats-new пометил как 'updated'. Bundle
> nodes-chunk 304 → 306 KB.

✅ **Правильно (для человека):**
```
✅ Что изменилось:
Тема «Инструменты Claude» стала намного подробнее — теперь там живой
пример, пошаговый сценарий и частые ошибки. И появились ссылки на 4
связанные темы, чтобы было удобно переходить.

💡 Почему так лучше:
Раньше это была пара строк — человек не понимал тему до конца. Теперь
видно глубину: это уже похоже на справочник, а не на список названий.

➡️ Что дальше:
Так же дополнить ещё две соседние темы — «Память» и «Размышление».
```
_(Технические детали — хеш коммита, имена файлов, размер — ушли в текст коммита.)_

### Пример 2 — серьёзное изменение (затронута безопасность и деньги)

✅ **Правильно (для человека):**
```
✅ Что изменилось:
Теперь рабочие схемы пользователей сохраняются в облаке, а не только на
их устройстве. Каждый видит и меняет только свои — чужие недоступны.

💡 Почему так лучше:
Раньше схема жила только в браузере — почистил историю, и она пропала.
Теперь она привязана к аккаунту и доступна с любого устройства.

⚠️ Важно знать:
Когда схемы начнут реально запускаться через платный сервис — каждый
запуск будет стоить денег. Пока этого нет, всё бесплатно.

➡️ Что дальше:
Сделать страницу со списком сохранённых схем, чтобы между ними удобно
переключаться.
```
_(Технические детали — таблицы, правила доступа, шифрование ключей — в коммите.)_

## Тон и стиль (для итога в чат)

- **Русский язык** (правило CLAUDE.md § 14a)
- **Как объясняешь не-программисту** — родителю, другу, клиенту
- **Короткие предложения** — лучше 3 коротких, чем 1 длинное
- **Через пользу для человека**, а не через устройство системы
- **Ноль терминов разработчика** — см. словарь выше
- Конкретика без жаргона: «страница грузится быстрее» > «оптимизировали bundle»

---

## Где это правило живёт

- **`CLAUDE.md` § 14b** — загружается автоматически в каждой сессии
- **`skills/post-action-summary/SKILL.md`** — эта детальная спека
- Технические детали каждого действия — в **тексте git-коммитов**

---

## Контроль качества

Две проверки перед отправкой итога:

1. **«Поймёт ли мама?»** — если в итоге есть слово, которое непрограммист
   погуглит — заменить по словарю. Это bug, если термин просочился в чат.
2. **«Не забыл ли вообще?»** — если после действия не написал итог — это
   тоже bug. Пользователь может сказать «итог» / «summary» — даю
   retro-итог прошлого действия в правильном формате.
