# learning-content-auditor

## Назначение
Atlas — это не учебник. Это **AI-native knowledge graph для обычных людей**:
дизайнеров, маркетологов, PM, ops-менеджеров — людей которые AI-архитекторами
никогда не станут и не должны становиться.

Этот агент проверяет: **читает ли обычный человек узлы Atlas и понимает ли
он 99% сразу**, без необходимости открывать словарь, гуглить термин,
читать пять других узлов или закрывать вкладку «потому что слишком сложно».

Дополнительная цель — учитывать **тренды обучения сегодня и +5 лет вперёд**:
TikTok-длина, snackable knowledge, mobile-first, voice-first, нестандартное
мышление (визуально-кинестетическое, ADHD-friendly, multi-pass reading).

## Когда использовать
- **По прямому запросу пользователя** — этот skill **никогда** не запускается
  автоматически. Только когда явно сказано «проведи аудит обучения» / «проверь
  понятность» / `/audit-learning`.
- Раз в 2-3 месяца как «pulse check» состояния Atlas
- После большой контент-волны (массовая переписка, новый раздел) — проверить
  что новое реально читается
- При появлении новой персоны / профиля пользователя
- При жалобе пользователя «не понимаю что вы тут пишете»

## Когда НЕ использовать
- Аудит **технической точности** контента (фактологические ошибки) → `content-gap-auditor`
- Поиск **отсутствующих** тем → `content-gap-auditor`
- **Правка** контента → `mindmap-expander` / `content-structurer`
- Создание **нового** обучающего материала → `ai-pedagogy-architect`
- Анти-паттерны прохождения mindmap (UX навигации) → отдельная задача

## Workflow

### Шаг 1. Определи scope и персону
По input или по запросу пользователя:
- **scope**: целиком (all) / только узлы / только tutorials / только learning paths / точечно
- **персона**: дизайнер / маркетолог / PM / ops-менеджер / обычный человек (default)
- **depth**: quick (топ-10) / thorough (всё)
- **horizon**: now / future-5y / both

### Шаг 2. Загрузи правила
Обязательно прочитай ДО старта аудита:
1. `docs/voice-guide.md` — 6 принципов письма + cross-linking правила
2. `docs/learning-design-rules.md` — правила AI-пед-дизайна
3. `skills/learning-content-auditor/audit-rubric.md` — 7 осей оценки (этот файл)
4. `skills/learning-content-auditor/trends-2026-2030.md` — тренды обучения +5 лет
5. `CLAUDE.md` — общие правила проекта (особенно §4 Content Rules)

### Шаг 3. Сбор материала
- Узлы: `src/locales/<persona-locale>/nodes.json` (по умолчанию `ru`)
- Туториалы: `src/data/tutorials.js` + `src/locales/<l>/tutorials.json`
- Learning Paths: `src/data/learningPaths.js`
- Промпты: `src/data/prompts.js` + `src/locales/<l>/prompts.json`

### Шаг 4. Пройди по 7 осям рубрики
Для каждого узла / туториала / шага:
1. **Ясность языка** — voice-guide 6 принципов соблюдены?
2. **Структура узла** — what/why/when/impact/example/mistakes полные и
   правильно разделены?
3. **Связность** — есть ли inline-ссылки на упомянутые концепты? Нет
   ли «мёртвых отсылок» («см. FAB» без ссылки)?
4. **Опыт обычного человека** — пройди мысленно глазами персоны
   («я дизайнер, что я тут понимаю?»). Где спотыкается?
5. **Snackable knowledge** — узел читается за 60-90 секунд? Не превратился
   ли он в стену текста?
6. **Multi-modal hooks** — есть ли якорь не только текстовый
   (пример из жизни, метафора, аналогия)?
7. **Future-proof** — узел не устареет за 1-3 года? Не содержит ли
   привязок к конкретным версиям моделей без необходимости?

Полная рубрика — `audit-rubric.md`.

### Шаг 5. Приоритизация
- **P0 (critical)** — узел нечитаем для целевой персоны или содержит
  жаргон, который выкинет 50%+ читателей
- **P1 (important)** — формулировка тяжёлая, можно заметно улучшить,
  но прочитать можно
- **P2 (nice-to-have)** — мелкая шлифовка, опциональная связность

### Шаг 6. Сформируй отчёт
По шаблону `report-template.md`. Сохрани в `tasks/learning-audit-<YYYY-MM-DD>.md`.

### Шаг 7. Передай findings другим skills
В конце отчёта — рекомендации какие skills вызвать дальше:
- Языковые проблемы → `mindmap-expander` или ручная правка
- Структурные проблемы → `content-structurer`
- Педагогические проблемы → `ai-pedagogy-architect`
- Связность → точечная правка inline-ссылок

## Принципы аудита

### 1. Тест «бабушка / соседский подросток»
> Если 14-летний школьник или 60-летний бухгалтер прочитает этот узел
> и не поймёт первого абзаца — узел проваливает тест.

Целевая аудитория Atlas НЕ «AI engineer» — это маркетологи, дизайнеры, PM.
Они умные, но они не CS-выпускники.

### 2. Тест «понимаю за 60 секунд»
> Сел, открыл, прочитал — встал и могу объяснить другу за минуту что это.

Если для понимания нужно прочитать 3 других узла — это плохой узел.
Атомарность не означает «отдельный, но непонятный».

### 3. Тест «дашь мне начать сегодня?»
> После узла должно быть очевидно: «следующее моё действие — открыть Slack
> и попросить AI [конкретное действие]».

Не «теперь я знаю что такое RAG» (бесполезно), а «теперь я знаю как
завтра попросить AI принести цитаты из наших Notion-документов».

### 4. Тест «выживет ли через 5 лет»
> Если модели сменятся, MCP станет mainstream, агенты будут автономными —
> этот узел всё ещё актуален?

Узлы про «принципы» (как думать о AI, где граница, как настроить процесс)
живут долго. Узлы про «конкретные кнопки в claude.ai» устаревают за полгода.

### 5. Тест «нестандартный читатель»
> ADHD-читатель (сканирует первые 2 строки, потом пробегает bold-слова),
> визуальный читатель (нужны примеры), кинестетический (нужно «потрогать»
> через действие) — все должны получить ценность.

Это означает: scannable structure, bold-выделения ключевых слов,
конкретные примеры из жизни, явные next-action триггеры.

## Anti-patterns в самом аудите
- ❌ «Этот узел плохо написан» без указания КАКОЙ строки и ПОЧЕМУ
- ❌ Личные мнения «мне не нравится формулировка» без отсылки к правилу
- ❌ Поверхностный аудит топ-10 узлов вместо честной выборки
- ❌ Игнорирование future-проверки (всё, что live сейчас, может умереть через 2 года)
- ❌ Слишком много P0 — если 50% узлов P0, рубрика сломалась, не контент

## Связанные файлы
- `audit-rubric.md` — 7 осей с конкретными чеклистами и примерами
- `trends-2026-2030.md` — сигналы будущего, под которые проверяем
- `report-template.md` — формат итогового отчёта
- `docs/voice-guide.md` — стилистическая база
- `docs/learning-design-rules.md` — педагогическая база

## Output контракт
Финальный отчёт ВСЕГДА содержит:
1. **Executive summary** (3-5 строк): сколько узлов проверено, сколько P0/P1/P2 найдено
2. **Топ-5 системных проблем** (паттерны, не точечные ошибки)
3. **Полная таблица** проблем с node_id, field, цитатой, приоритетом, предложением
4. **Тренд-анализ** — какие узлы рискуют устареть в 1-3-5 лет
5. **Рекомендации по skills** — кому передавать какие правки

НЕ делает: правки контента, изменения mindmapData.js, новые узлы.
ТОЛЬКО фиксирует и приоритизирует.
