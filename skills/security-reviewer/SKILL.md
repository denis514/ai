# security-reviewer

> Ревьюер сегмента «Данные и безопасность»: RLS, миграции, секреты, шифрование.
> Вызывается из `quality-gate`. Любая дыра здесь — block.

---

## Зона ответственности
`docs/agent-builder/migrations/*.sql`, любые таблицы `builder_*`,
`supabase/functions/_shared/{auth,crypto}.ts`, работа с ключами/токенами,
публичные edge-функции, формы и запросы к Supabase в клиенте.

## Чек-лист (severity по умолчанию = block для нарушений)

**🔒 RLS:**
- Каждая новая таблица: `ENABLE ROW LEVEL SECURITY` + политика owner-only
  (`auth.uid() = user_id`, и USING, и WITH CHECK).
- Клиентские запросы полагаются на RLS, а не на фильтр в JS как единственную защиту.

**🗝️ Секреты и ключи:**
- Ключи/токены хранятся зашифрованными (AES-GCM, `BUILDER_KEY_ENCRYPTION_SECRET`);
  расшифровка только на сервере; не логируются; не возвращаются клиенту; не в URL.
- Публичная функция (`--no-verify-jwt`) обязана сама проверять секрет
  (`x-builder-cron`/`x-builder-service`) или токен (вебхук). Нет проверки → block.

**🗃️ Миграции и данные:**
- Soft-delete учтён: при «удалении» схемы её зависимости (расписания/вебхуки)
  чистятся/гасятся; FK `ON DELETE CASCADE` не «спасает» при архивации.
- Нет необратимой потери данных без явного намерения; нет молчаливого удаления.
- Имена колонок реальны (частая ошибка: `created_at` vs `started_at`).

**🌐 Сетевое:**
- SSRF-защита при выборке по URL (блок localhost/private/metadata).
- Данные не уходят на адреса/формы, пришедшие из недоверенного контента.
- CORS/секреты вебхука: ссылка длинная, отзываемая, анти-флуд.

**🔏 Приватность (правила проекта):**
- Никаких персональных данных в URL/логи; cookie/consent — privacy-preserving.
