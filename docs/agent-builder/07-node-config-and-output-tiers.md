# 07 — Node configuration + output tiers + result delivery

> Стратегия двух связанных тем, поднятых при тестировании B-2.2:
> (1) как пользователь настраивает узлы (свои промпты / skills / значения);
> (2) как контролировать расход токенов через **размер результата** и
> отдавать результат скачиваемым, с обучающим сопровождением.
>
> Дополняет `04-beta-90day.md` (там — месячные лимиты/биллинг, тут — per-run
> экономия и UX результата). Дата: 2026-05-28.

---

## Часть A — Конфигурация узлов в режиме построения

### Проблема
Сейчас узлы — это «роли» без редактируемого содержимого. Реальный запуск
использует встроенные инструкции (Path A). Чтобы продукт был полезным,
пользователь должен **настраивать** узлы: свой промпт, свои данные, свои skills.

### Три уровня настройки (по возрастанию сложности)

**Уровень 1 — Инструкция узла (промпт).** *(ближайший шаг, Path B)*
- Клик по узлу → в боковой панели редактируемое поле «инструкция».
- Пусто → используется встроенная роль-инструкция (как сейчас).
- Заполнено → переопределяет. Сохраняется в `config.prompt` узла (уже есть
  поле `config` в схеме `builder_workflow_nodes`).

**Уровень 2 — Значения (переменные).** *(следующий)*
- На узле-триггере пользователь задаёт именованные значения: `{{бренд}}`,
  `{{ниша}}`, `{{ссылка}}`.
- В инструкциях узлов можно ссылаться `{{бренд}}` → подставляется при запуске.
- Это превращает workflow в **шаблон**, который переиспользуется с разными данными.

**Уровень 3 — Свои Skills.** *(позже)*
- Пользователь сохраняет именованную инструкцию как «skill» (мини-SKILL.md):
  название + текст + опц. примеры.
- Skill можно прикрепить к любому агент-узлу (как пресет инструкции).
- Библиотека skills пользователя хранится в Supabase (новая таблица
  `builder_user_skills`, owner-RLS).
- Это мост к Atlas-контенту: готовые workflow Atlas → импортируемые skills.

### Что НЕ делаем сейчас
- Загрузка файлов/документов в узлы (vision/file_read) — это реальные tool-
  интеграции = Phase B-3.
- Маркетплейс skills между пользователями.

## Часть B — Размер результата = контроль токенов (КЛЮЧЕВАЯ ИДЕЯ)

### Проблема
Реальный запуск тратит деньги пользователя. Нужно дать **явный контроль**:
сколько потратить и что получить. Решение — выбор размера результата **перед
запуском**, с понятным объяснением и оценкой стоимости.

### Три размера (tiers)

| Размер | Что получаешь | Токены/узел | Стоимость | Доставка |
|--------|---------------|-------------|-----------|----------|
| **S — Кратко** | Сжатый готовый текст | ~512 | минимум | Копировать в буфер |
| **M — Документ** | Один структурированный документ | ~2048 | средне | Скачать .md |
| **L — Полный** | Разбивка по разделам/файлам | ~4096+ | максимум | Скачать набор файлов (.zip) |

Технически tier управляет:
- `max_tokens` на каждый агент-вызов;
- для **L** — финальный узел может разложить результат на части (по разделам)
  → несколько файлов.

### Экономный MVP (как тестировать дёшево)
1. **По умолчанию — S** (самый дешёвый). Первые реальные запуски стоят центы.
2. **Оценка перед запуском**: «≈ N узлов × лимит = до ~X токенов (~$Y)».
   Считается локально, без вызова API — бесплатно.
3. **Подтверждение** в окне ввода: размер + оценка + «Запустить».
4. Жёсткие потолки `max_tokens` по tier — нельзя случайно «убежать».

### Почему это правильно для продукта
- Пользователь **сам решает** глубину vs стоимость — нет сюрприза в счёте.
- S-режим = «попробовать почти бесплатно» → снижает барьер первого запуска.
- L-режим = «серьёзный артефакт» → ценность, за которую платят.

## Часть C — Доставка результата + скачивание

### Отображение
- ExecutionPanel после запуска показывает **финальный результат** (рендер
  markdown), не только логи.
- Кнопки: **Копировать** (всегда), **Скачать** (M/L).

### Форматы по tier
- **S** → текст, кнопка «Копировать».
- **M** → один `.md` файл, кнопка «Скачать».
- **L** → несколько файлов (по разделам) → `.zip` через клиентскую упаковку
  (без новых зависимостей — Blob API; zip — лёгкая lib или просто несколько
  отдельных скачиваний для MVP).

### MVP-упрощение для L
Чтобы не тянуть zip-зависимость сразу: на первом этапе **L** отдаёт один `.md`
с явными разделами (`## Раздел 1`, `## Раздел 2`), а «разные файлы» —
следующая итерация. Так пользователь уже получает полноту, мы не усложняем.

## Часть D — Обучающее сопровождение (обязательно)

Каждый шаг сопровождается коротким объяснением простым языком:
- **Выбор размера**: «Кратко — быстрый ответ, почти бесплатно. Документ —
  готовый файл. Полный — подробная разбивка, дороже.»
- **Оценка стоимости**: «Этот запуск потратит примерно столько-то — это с
  твоего ключа.»
- **После результата**: «Готово. Можешь скопировать или скачать. Дальше —
  попробуй изменить инструкцию узла или запустить с другими данными.»

Цель: пользователь всегда понимает **что он делает, сколько это стоит и что
дальше** — без терминов.

## Предлагаемая последовательность (от дешёвого теста к полноте)

**Шаг 1 — Размеры результата + оценка + S-режим** *(сначала, чтобы тестировать дёшево)*
- Селектор S/M/L в окне ввода + локальная оценка токенов + подтверждение.
- Backend: `builder-execute` принимает `tier` → ставит `max_tokens`.
- Доставка S: показ результата + «Копировать».
- **Результат: можно безопасно делать первый реальный запуск за центы.**

**Шаг 2 — Скачивание (M)**
- Финальный результат как `.md`, кнопка «Скачать».

**Шаг 3 — Редактирование инструкции узла (Path B, Уровень 1)**
- Поле инструкции в сайдбаре, сохраняется в `config.prompt`.
- `builder-execute` использует `config.prompt` если задан, иначе роль-дефолт.

**Шаг 4 — Значения/переменные (Уровень 2)**
- `{{переменные}}` на триггере + подстановка.

**Шаг 5 — L-режим (многофайловый) + свои Skills (Уровень 3)**
- Разбивка результата, zip, библиотека skills.
