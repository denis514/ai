# 14 — Позиционирование: Builder vs claude.ai + дорога к настоящей автоматизации

> Дата: 2026-05-29. Источник правды по вопросу «зачем Builder, если есть claude.ai».
> Читать вместе с 09-automation-vision.md и ADR-0006 (монетизация BYOK).

---

## 1. Честная граница: где Builder НЕ нужен

Если задача = «человек сам открывает чат и спрашивает Claude» — **claude.ai лучше**,
и Builder не добавляет ничего, только тратит токены. Проекты в claude.ai уже дают
постоянные инструкции и контекст для **ручного диалога**. Не пытаемся конкурировать
здесь. Целиться в «ещё один чат с Claude» = смерть продукта.

## 2. Где Builder незаменим (наша единственная причина существовать)

claude.ai принципиально не умеет четыре вещи. Это и есть наш ров:

| Разрыв | claude.ai | Agent Builder |
|---|---|---|
| **Без человека** | ждёт, пока ты напишешь | запуск по расписанию/триггеру, **работает пока ты спишь** |
| **Оркестрация** | один ассистент, один диалог | конвейер из агентов + условия + циклы + маршрутизация |
| **Повторяемость / передача** | твой личный чат | сохранил схему → запускаешь одинаково 100×, отдал не-кодеру |
| **Авто-доставка** | ответ в окне, копируешь руками | итог сам уходит в Telegram / почту / календарь / таск-трекер |

**Формула позиционирования:**
> Builder — это **не «лучше чат»**. Это **автоматизация без человека**:
> «запусти и забудь / по расписанию / отдай команде / много шагов с логикой».

Каждая фича и каждый шаблон сверяются с этим. Если фича помогает «поболтать» —
она не наша. Если помогает «работает само и доставляет результат» — наша.

## 3. Критическое требование: запуск НЕ зависит от компьютера пользователя

Сегодня реальный запуск инициируется из браузера (клиент дергает edge-функцию).
Это значит: **закрыл вкладку — ничего не идёт.** Для настоящей автоматизации это
блокер №1. Цель:

> Пользователь включил автозапуск (например «каждое утро в 8:00») → **выключил
> компьютер** → система на сервере всё равно сама запускает схему и доставляет
> результат.

Это сдвиг с «клиент-триггера» на **серверный планировщик**.

### Что для этого нужно (архитектурно, без кода)
1. **Хранилище расписаний** — таблица: workflow_id, тип триггера (cron/время/вебхук),
   параметры, вкл/выкл, владелец.
2. **Серверный планировщик** — cron на стороне сервера (Supabase scheduled functions /
   pg_cron / внешний cron), который сам вызывает `builder-execute` по расписанию,
   без участия браузера.
3. **Вебхук-вход** — публичный endpoint, который запускает схему по внешнему событию
   (форма, заказ, сообщение).
4. **Журнал и уведомления** — что запускалось, успех/ошибка, доставка статуса.
5. **Лимиты и безопасность** — троттлинг, потолок токенов на пользователя (защита
   кошелька), отключение «убежавших» циклов.

## 4. Песочница → продакшн (как пользователь растёт)

- **Песочница (сейчас):** «Демо» без токенов + «Реально» вручную. Эксперименты.
- **Автоматизация (цель):** тот же workflow ставится «на расписание/триггер» и
  живёт на сервере. Одна и та же схема — сначала играешь, потом «включаешь».

## 5. Дорожная карта возможностей (приоритеты)

**Триггеры (вход):**
- [ ] Время/расписание (cron) — «каждый день / по будням / раз в час». ⭐ ядро автоматизации.
- [ ] Вебхук — запуск по внешнему событию.
- [ ] Ручной (есть).

**Коннекторы (выход и данные):**
- [x] Telegram (доставка) — готово.
- [ ] Email (доставка).
- [ ] Календарь (создать событие/напоминание).
- [ ] Таск-трекер / Sheets / Slack — позже.

**Инструменты-способности (вход данных):**
- [x] Web Search, Память, Файлы, Vision — работают.
- [ ] Calendar read, MCP-коннекторы к внешним API — «играй в песочнице».

**Инфраструктура исполнения:**
- [ ] Серверный планировщик (runs continue when computer is off) — ⭐ блокер автоматизации.
- [ ] Журнал запусков + уведомления об ошибках.
- [ ] Потолок токенов/частоты на пользователя.

## 6. Главный вывод

Atlas учит «понять», Builder даёт «сделать по-настоящему и автоматически».
Ценность платформы (за неё платят, ADR-0006) = **оркестрация + серверная
автоматизация + доставка в рабочие инструменты**, чего голый claude.ai не делает.
Без серверного планировщика Builder остаётся «красивым чатом» — поэтому
**серверный запуск по расписанию = приоритет №1** на пути к продукту.
