# 12 — Стратегия связей: аудит против Flowise (AgentFlow v2)

> Дата: 2026-05-29. Источник сравнения — живое исследование Flowise
> (cloud.flowiseai.com, Agent Canvas v2) + наша текущая модель
> (`10-node-capability-model.md`, `connectionRules.js`, `nodeCapabilities.js`).
> Цель: НЕ копировать, а усилить нашу модель там, где это совпадает с нашей
> обучающей философией (Atlas как knowledge layer).

---

## 1. Краткий вердикт

Наша модель связей **сильнее по обучаемости и дружелюбию**, Flowise — **строже и
чище по «грамматике» графа**. Главные осознанные различия:

| Аспект | Flowise | Atlas Builder | Кто «лучше» под нашу цель |
|---|---|---|---|
| Направление | жёстко слева→направо, порт-тип по стороне | плавающие концы, тянуть с любой стороны, направление = откуда тянул | **Atlas** (интуитивнее новичку) |
| Инструменты | спрятаны в поля узла (чистый холст, но не видно) | видимый узел + ATTACH-связь | **Atlas** (видно = обучает) |
| Поток данных | переменные `(x)`, провода = только порядок | пока цельный текст-контекст по связям | **Flowise** (гибче) → наш C5 |
| Ветвление/циклы | явные узлы Condition/Iteration/Loop | пока нет, только запрет циклов | **Flowise** (наш пробел) |
| Запрет связи | молча «отскакивает» | блок по правилам, но тоже без причины | ничья → **повод усилить нас** |
| Направление-стрелка | нет наконечников | анимированный градиент-поток | **Atlas** |
| Валидация перед запуском | Checklist, но пропускает required-поля | наша C1 ловит и структуру, и пустые | **Atlas** |
| Знание о узле | описание в палитре | тултип + превью узла Atlas + «Learn more» | **Atlas** (уникальный слой) |

Вывод: **не перенимаем** скрытие инструментов и жёсткую лево→право-решётку — это
убьёт наши преимущества. **Перенимаем** то, что закрывает наши реальные пробелы.

---

## 2. Что взять (приоритизировано) — «улучшить нас, не дублировать»

### A. Явные узлы управления потоком (наш главный пробел) — категория `logic`
Flowise делает циклы/ветвления **отдельными узлами**, а не обратными линиями.
Это идеально ложится на наш принцип «DATA — это DAG, циклы запрещены»:

- **Condition** — ветвление по правилу (`если результат содержит X → ветка A, иначе → B`).
  Несколько выходных портов = веток. Детерминированно.
- **Condition Agent** — «пусть агент сам решит, по какой ветке идти» (наша фишка —
  агент-маршрутизатор, отлично для мультиагентности).
- **Loop (bounded)** — возврат к узлу с **обязательным лимитом** (`Max Loop Count`,
  по умолчанию 5) + `Fallback`. Цикл без риска бесконечности — ровно наша философия
  безопасности.
- *(позже)* **Iteration** — контейнер «прогнать вложенное N раз».

Почему это нас усиливает: сейчас мы умеем только линейные/разветвлённые DAG.
Реальные автоматизации требуют «если/иначе» и ограниченных повторов. Делая их
**явными узлами**, мы сохраняем читаемый и анализируемый граф (не ломаем
isValidConnection и pre-run валидацию).

### B. Объяснять, ПОЧЕМУ связь нельзя (превратить слабость Flowise в нашу силу)
У Flowise недопустимая связь молча отскакивает. У нас — то же (isValidConnection
возвращает bool). Но у нас уже есть `denyReasonKey(code)` в `connectionRules.js`.
Надо **показывать причину**: при неудачном соединении — короткий тост/подсказка
(«Нельзя соединить инструмент с выходом», «Эти узлы уже связаны», «Получился бы
цикл — используйте узел Loop»). Это и UX, и обучение в одном.

### C. Переменные `{{...}}` в задаче/инструкциях (= наш пункт C5)
Flowise передаёт данные подстановкой `(x)`. Нам это нужно для **переиспользуемых
схем**: `{{бренд}}`, `{{url}}`, `{{дата}}` в инструкции/задаче → одна схема под
разные входы. Связь по-прежнему задаёт порядок, а значения протаскиваются
выражениями.

### D. Паттерн «ограниченного цикла» как стандарт безопасности
Любой будущий механизм повтора у нас обязан иметь лимит + fallback (как
`Max Loop Count`). Фиксируем как правило в capability-модели.

---

## 3. Что НЕ брать (сохранить наши преимущества)

1. **Скрытие инструментов в поля узла.** Flowise так делает «чистый холст», но
   теряет наглядность. У нас инструмент = видимый узел с ATTACH-связью — это
   **обучает** (видно, что агент «умеет искать в вебе»). Сохраняем. При росте
   числа инструментов — добавить на узел-агент **компактные значки прикреплённых
   способностей** (читаемость без потери наглядности).
2. **Жёсткая лево→право-решётка + типизированные стороны портов.** Наши плавающие
   связи и «тяни с любой стороны» дружелюбнее. Сохраняем.
3. **Связи без стрелок.** У нас анимированный градиент-поток — направление видно.
   Сохраняем.
4. **Молчаливый UI / непостоянные кнопки.** Избегаем (см. п. 2.B).

## 4. Где мы уже впереди (валидация нашей стратегии)

- Плавающие связи + соединение с любой стороны + направление «как нарисовал».
- Видимое прикрепление инструментов (обучающий слой).
- Анимированный направленный поток вместо «голых» линий.
- Pre-run валидация (C1) ловит больше, чем Flowise Checklist.
- Связь с Atlas: у каждого узла — превью знания и «Learn more». У Flowise только
  строчка-описание; у нас — целый knowledge layer. Это **наш ров** (moat).

## 6. Влияние на capability-модель

- Новый kind `logic` (или роли внутри): `condition`, `condition-agent`, `loop`.
- `condition`: вход DATA(1), выходы DATA(≥2, по веткам) — динамические порты.
- `loop`: вход DATA(1), выхода нет (терминальный); цель + лимит — в config.
- Pre-run валидация: предупреждать о ветке без приёмника, о Loop без цели/лимита.
- DAG-инвариант сохраняется: «возврат» выражается узлом Loop, а не обратным ребром.
