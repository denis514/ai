## Стратегическая рамка

Atlas позиционируется как «AI Transformation Playbook for Product/Ops teams»
(см. product-audit-2026-05-24 § funny truth).

**Product/Ops lead** не покупает «список фич Claude». Он покупает **operating models**.
Capabilities ему нужны только **в контексте workflow**:

- `cap-vision` → актуален в `ec-pdp-gen` (анализ product image), `ds-design-research` (скриншоты UX), `mk-content-ops` (creative review)
- `cap-files` → в `pr-discovery-research` (PDF-парсинг), `ec-merchandising` (catalog CSV)
- `cap-search` → в `mk-campaign-intel`, `cs-knowledge-base`
- `cap-memory` → в `ec-personalization`, `cs-team-workflow`
- `cap-computer` → в `ec-checkout-opt`, `ops-process-automation`
- `cap-tools` → база MCP/agents — **strategically critical**
- `cap-caching` → в `sys-cost-management`, `sc-data`
- `cap-citations` → в `pr-feedback-synthesis`, `cs-knowledge-base`
- `cap-code-exec` → в `sc-data`, `pr-product-analytics`
- `cap-thinking` → meta — влияет на выбор модели (Opus thinking vs Sonnet)
- `cap-limitations` → **обязательное знание для всех ролей**

Вывод: **большинство cap-узлов = справочник, не value-add**. Они нужны как
референс **при чтении transformation-узла**, не как самостоятельная ветка.

## Решения по узлам

### KEEP AS-IS (1 узел)

#### ✅ `cap-limitations`
**Не трогаем.** 721 chars богатого контента с конкретными ограничениями
(дата среза, hallucinations, контекст, no-internet и т.д.). Один из самых
полезных узлов в Foundation. Каждый ICP-пользователь должен это прочитать.

**Action:** `minLevel: 'beginner'` — поднять видимость, не понизить.

---

### UPGRADE — переписать с богатым контентом (3 узла)

#### ⬆️ `cap-tools`
**Стратегически критичен.** Это база MCP, agents, skills, Claude Code — всего
что делает Claude «больше чем чат». Сейчас 129 chars — недопустимо.

**Что нужно в upgrade:**
- что: function calling механика + JSON-схема
- зачем: база интеграций
- когда: триггеры (нужны actions, не только тексты)
- impact: примеры на разнице «без tools» vs «с tools»
- example: workflow с tool calls (booking system, CRM lookup)
- mistakes: tool design анти-паттерны (vague descriptions, too many tools)

**Estimated effort:** 1.5 часа × 3 локали ≈ 4-5 часов.

#### ⬆️ `cap-thinking`
**Влияет на model selection.** Сейчас факт «есть thinking mode», без сигнала
когда включать. Это решение часто принимается неправильно (включают везде или нигде).

**Что нужно в upgrade:**
- что: extended thinking, как работает
- зачем: для каких задач thinking реально помогает
- когда: **decision criteria** — multi-step reasoning, math, code review, ambiguity
- impact: time + cost trade-off (5× медленнее, 2-3× дороже)
- example: правильный/неправильный случай применения
- mistakes: «включаю везде по умолчанию» / «не включаю никогда»

**Estimated effort:** 1.5 часа × 3 локали ≈ 4-5 часов.

#### ⬆️ `cap-memory`
**Deprecate-watch + upgrade.** «Постепенно раскатывается» устарело за полгода —
Memory сейчас доступна в claude.ai на части тарифов. Требует факт-чек на дату
upgrade'а + переписку с актуальным статусом.

**Что нужно в upgrade:**
- что: long-term memory механика, claude.ai vs API
- зачем: для каких use cases (personalization, team context, project continuity)
- когда: триггеры для включения
- impact: cross-link на `ec-personalization`, `cs-team-workflow`
- example: реальный сценарий когда Memory меняет UX
- mistakes: privacy implications, memory pollution

**Estimated effort:** 1.5 часа × 3 локали ≈ 4-5 часов.

---

### RELOCATE / REFRAME (1 узел)

#### 🔁 `cap-caching`
**На текущем месте малополезно.** Это не «возможность Claude», а **рычаг оптимизации
стоимости** при работе с большим контекстом. Принадлежит ближе к `sys-cost-management`
или к `platform`.

**Action:** оставить узел в `capabilities` (не ломать ссылки), но:
1. Переписать ракурс с «фича Claude» на «cost lever»
2. Добавить relatedIds к `sys-cost-management`, `sc-data`, `ec-pricing`
3. Title опционально: «Prompt caching (cost optimization)»

**Estimated effort:** 1 час × 3 локали ≈ 3 часа.

---

### CONSOLIDATE — 5 узлов в 1 (5 → 1)

#### 🔄 `cap-input-modalities` (NEW node)

**Объединяет:** `cap-vision` + `cap-files` + `cap-search` + `cap-citations` + `cap-code-exec`

**Логика:** все 5 — это «что Claude может принять/обработать как input или output».
По отдельности — stub. Вместе — comprehensive overview «What Claude can ingest and process».

**Структура нового узла:**
- title: «Возможности ввода и обработки» / "Input modalities and processing"
- what: 4 канала (текст, изображения, файлы, web) + 2 спец-режима (citations, code execution)
- зачем: понять что Claude может работать не только с текстом
- когда: тригерры выбора каждого канала
- impact: примеры на каждый канал из transformation-узлов
- example: multi-modal workflow (PDF + image + web search в одном flow)
- mistakes: типичные ошибки выбора modality

**Что делать со старыми 5 узлами:**
- Не удалять немедленно (поломают cross-links из других узлов)
- Перенаправить через redirect: оставить `cap-vision/files/search/citations/code-exec` как stubs со ссылкой «→ cap-input-modalities»
- Через 2-3 месяца — оценить, можно ли удалить полностью

**Estimated effort:** 2 часа на новый узел × 3 локали ≈ 6 часов + 1 час на stub-redirects.

---

### DEFER / HIDE (1 узел)

#### ⏸️ `cap-computer`
**Beta-фича на API, не доступна для большинства пользователей.** Для ICP
(product/ops lead) — нерелевантно: они не работают с Claude через API.

**Action:**
1. `minLevel: 'expert'` — скрыть из default-просмотра
2. Добавить пометку в title или what — «(API beta)»
3. Deprecate-watch на каждый release Anthropic — если статус меняется, пересмотреть
4. Если через 6 месяцев всё ещё beta — рассмотреть удаление
